Two actions on every email

Every actionable line in the inbox monitor carries the same two buttons: raise it as a Zoho ticket, or reply to the whole thread asking for what a ticket needs. Both open a dialog with every field already filled in and every field editable. This page is clickable, and nothing on it contacts Zoho or your mailbox.

Create ticket

Status, title, tag, release date, owner and description, all pre-filled. The description is composed rather than pasted: type, who asked, who reported it, when, the scope, and the documents. Correct a name in the dialog and the description rewrites itself — the two can never disagree.

Three things happen in order, and the plan stops at the first failure: the Zoho task, one line in the sprint tracker, then an acknowledgement left in your Drafts telling the thread the ticket number and the release date.

Ask for context

A reply to everyone on the thread, pre-composed, asking for the full name of whoever reported it, the project or record it happened in, the date, and any documentation. It asks only for what the email did not already say.

What fills each field, and why

The ticket

titleSuggested from the subject, stripped of RE: and bracket noise. Never chosen for you — a title is read by people who never saw the email.
statusYour portal's full list, with Ready for Development selected. The list is configuration; a status that is not on it is refused before anything is sent, because Zoho rejects an unknown status with an error that names no alternatives.
tagThe computed sprint. Changing it moves the release date with it.
release dateThe sprint's Wednesday. Editable, but a date that no longer matches its sprint is flagged.
ownerDefaults to Unassigned — see below.
descriptionComposed to the fixed shape on the right.

The sprint rule

A ticket belongs to the next Wednesday strictly after the day it is created.

On owner — my recommendation

Default to Unassigned, not to you and not to the sender. At Ready for Development the sprint is the queue: whoever picks it up owns it. Pre-assigning quietly makes that person accountable for work they have not seen, and it is the one field where a wrong default causes an argument rather than an edit.

How the description is composed

Same shape on every ticket, so nobody has to read it end to end to find one fact.

LineFeature / changeBug
TypeDetected from the wording; you can flip it
Requested byThe person who made the request — the sender, unless the email says otherwise
Reported bynot shownThe person who hit the bug, usually not the sender
Reported onnot shownWhen it was reported; "Monday" is resolved to a date

CitationFrom / Received / Subject, and a link back to the email

A bug ticket will not be created half-blind

Reported by and Reported on are required on a bug, and almost never stated in the email. Milou guesses them from the wording and marks the guess; if it finds nothing, the field stays empty and the Create button stays disabled. That is what the second action is for — it goes and asks.

The alternative is a description that reads "Reported by: (unknown)", which is a question nobody will ever go back and answer.

The tracker is the most dangerous thing here

It is a Word document you maintain by hand. A ticket can be deleted and a mail can be recalled; quietly mangling a document you have been editing for months cannot be undone from here.

So Milou splices in one paragraph and copies every other byte across unchanged — no re-saving the file through a library that would reformat it. The new line is cloned from the line above it, so it keeps that section's bullets and numbering. If the sprint heading is not in the document, nothing is written: a line filed under the wrong sprint is harder to notice than a line that was never added. Running it twice adds nothing the second time.

Editing it needs Files.ReadWrite on its own credential, and the previous version of the file is kept before anything is uploaded.

The acknowledgement is a draft, on purpose

Once the ticket exists, its number is a better status channel than you are — so the draft points them at it, and gives the release date as the latest they should expect. A date stated without that qualifier gets read as a promise for that exact day, and chased on it.

It is saved to Drafts and never sent. That is a deliberate asymmetry: a draft is reversible and a sent mail is not, and this one goes out immediately after a ticket number was allocated a second ago. Creating it needs Mail.ReadWrite — wider than Mail.Send, and worth knowing, because the same grant can modify and delete mail.

The reply is a write, and is bounded like one

Sending needs MILOU_OUTLOOK_WRITE_TOKEN with Mail.Send — a separate credential from the read-only token the monitor uses, which cannot send. Approval is bound to the exact recipients and the exact wording; editing either clears it.

Adding or removing a recipient is the one edit that needs a wider Graph grant, so the dialog flags it rather than failing at send time.

Nothing on this page is real. No ticket number is allocated, no mail is sent, and the tracker line is not written anywhere. The two sample emails, the portal and the people are the same fixtures the test suite runs against.
