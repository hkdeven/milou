# Prototypes

Two HTML files. Open either in a browser; both are self-contained and neither
contacts anything.

## `milou-app.html` — the product, as if it were live

Generated by `scripts/build_prototype.py`. **Rebuild it after changing a routine,
a report, or the renderer:**

```
python3 scripts/build_prototype.py
```

Every report in it is produced by the routine that produces it in the running
application, rendered by `render_html.render_report` — the renderer the web view
uses — over the fixtures the test suite runs against. Nothing is redrawn by hand.
If a report looks wrong here, it is wrong in the product.

Each routine is built at the instant its own tests build it at, rather than at a
single shared clock, because a routine reads "3h ago" against the moment it ran.
One clock for all of them would render half the app as an empty week, which is a
rendering artefact and not something the product does.

What the prototype adds is the shell the application does not have yet:
navigation between routines, and the two actions on an inbox row. The dialogs
pre-fill themselves from the same intake logic the action uses, so the sprint
rule, the composed description, the extracted reporter and date, and which
questions the reply asks are all the product's own behaviour.

Pressing Create or Send changes nothing: no ticket is allocated, no document is
edited, no mail leaves any mailbox. The ticket number is invented on the spot so
the acknowledgement can show what substitution looks like. The "What is real
here" view in the sidebar says all of this again, in the page itself.

## `ticket-flow.html` — the annotated walkthrough

The same two actions, with the reasoning beside them: where each field comes
from, why a bug ticket refuses to be created without a reporter, why the owner
defaults to unassigned, why the acknowledgement is a draft rather than a send,
and what each credential can and cannot do. Hand-written, and the one place the
design arguments are written down next to the thing they argue about.
